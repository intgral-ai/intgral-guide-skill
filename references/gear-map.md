# Gear 之间的关系

需要确定谁参与、依赖什么、去哪里找资料时读取本文件。

## 关系模型

| 对象 | 连接到什么 | 需要确认的问题 |
|---|---|---|
| 公司目标 | 项目或阶段结果 | 这项工作为何值得做？成功证据是什么？ |
| 项目 | 工作任务、里程碑和依赖 | 本次范围、负责人和取舍是什么？ |
| 工作任务 | 一位推进负责人、协作角色、交付与验收 | 下一步是谁的动作？怎样知道完成？ |
| 人或角色 | 输入、执行、协调或决定 | 其职责和决定权是否在当前记录中明确？ |
| 来源 | 事实、决定、设计或实现 | 来源是否适用？是否已确认？读取时间是什么？ |
| 会议与日志 | 相关来源、历史更新、未决问题与明确行动 | 哪些是事实、提议或已确认结论？覆盖到何时？ |
| 决定 | 有权负责人、证据、取舍、受影响的计划与复核条件 | 谁确认？依据是什么？是否替代旧决定？ |
| 产物 | 原任务、验证证据和后续工作 | 结果放在哪里？谁接受？还阻塞什么？ |

父子关系表示拆分，依赖关系表示先后约束，来源链接表示证据。研究、商务、设计和工程可以彼此提供输入；依据具体工作选择路径。

## 通用角色导航

| 工作 | 建议咨询的职能 |
|---|---|
| 愿景、方向、研究开发 | 公司方向与研究负责人 |
| 研究证据、数据质量与测试 | 研究、数据和验证职能 |
| 商务方案、合作与商业条件 | 商务职能 |
| 客户问题、关系与反馈 | 客户关系职能 |
| 技术方案、依赖、实施协调 | 技术统筹职能 |
| 前后端交付与集成 | 工程职能 |
| 设计系统、UI/UX 与交互 | 产品设计职能 |

这些是导航类别，不是固定人员、组织层级或审批矩阵。使用私有配置和当前项目记录解析实际成员；缺少映射时提出建议而不替人指派。

## 平台之间如何配合

- Slack 中的请求连接到现有 Linear 任务或待澄清的问题。正式状态仍在 Linear。
- Linear 任务连接有关的 docs.intgral.ai 文档、Figma 设计版本和 GitHub PR。
- UI/UX 以 Figma 的适用设计系统、组件、状态和批准版本对齐。无法定位时先明确设计来源，避免猜测已批准的视觉规则。
- 商务与团队文档在 docs.intgral.ai 写作和维护。需要保存在 Drive 的附件或文件，通过有权限的原链接关联；不同受众的文档分别保持其访问范围。
- 代码评审、CI 与实现证据回到 GitHub。文档与任务引用这些证据，不复制一套可以独立修改的任务状态。
- 交付完成后，已授权的交接把产物链接带回原讨论；长期决定进入团队私有文档或 context。
- 会议纪要与每日 logs 串联历史 updates 和当前证据，为负责人决策提供输入；确认后的决定连接计划与任务，执行和验收结果再回到更新与复盘。详见 [会议、日志与决策](workflows.md#会议日志与决策)。

只维护任务需要的关系和少量原文链接。访问成功不等于内容已获批准，旧快照不等于当前状态，岗位名称也不自动赋予全部业务决定权。
