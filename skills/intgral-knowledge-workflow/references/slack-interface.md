# Slack 工作入口：线程召唤 agent，docs 保存长期记录

成员在 Slack 提问、确认、请求修改并查看结果。Agent 负责读取有关文档、维护有效记录并回帖；阅读 docs 链接是按需选择，不是完成工作的前提。原始 Slack 确认是来源证据，docs 保存当前有效的知识、范围和决定，正式任务状态仍由任务系统负责。

这是交互与执行规范。实际 agent 账号、可接收的频道、事件/轮询入口、执行身份、主题到文档的映射与启用状态从私有配置核实。读写 Slack 的连接器不等于已接入 Slack 召唤；`@agent` 在下文只是示例占位符。接收请求、执行写入及回帖均实测通过前，报告为待接入，不承诺自动响应。

## 成员怎样使用

在有关问题的原线程里用自然语言提出请求，无须复制 ID 或填表：

| 示例 | 行为 |
|---|---|
| `@agent 现在 MVP 的范围是什么？` | 核对有效文档与最近确认，在原线程回答 |
| `@agent 整理这个讨论，先给修改建议` | 返回问题、方案和进度；保持草稿 |
| `@agent 按我刚才的结论更新 MVP，工程方案也对齐` | 核验该成员对范围的确认权及目标权限，按授权写回有关文档 |
| `@agent 纠正刚才的记录：……` | 保留旧依据，核对并更新明确指定的内容 |

仅提及 agent、一般讨论、引用别人的命令或自动摘要，不构成修改/发布授权。收到明确改文档请求后，只在目标、来源和权限有实质缺口时追问；能从线程与已登记主题唯一定位的文档由 agent 查找。找不到唯一目标时在原线程给出候选，不重复新建文档。

## 哪些可直接写

| 请求与依据 | 执行 |
|---|---|
| 有来源的事实、归档、纠错；权限内的整理 | 已明确要求写回且目标可核实时，直接最小修改并读回复核 |
| 有权负责人明确确认范围/取舍并要求写回 | 同一条消息可同时构成决定依据和写入授权；无需额外一轮审批 |
| 仍在讨论的方案或批准权限不明 | 可以按授权保存同受众提案，保持待确认，不能改成有效决定 |
| 改变负责人、预算、期限、验收或正式任务 | 先核对对应确认权限与原始依据；正式任务还须满足 work_tracking 门槛 |
| 向更广受众发布、改变文档权限 | 单独核对准确内容、目标与有权批准；未获批先准备可审阅稿 |

确认权来自项目配置与已核验的职责；频道成员身份或文档可编辑权限本身不授予所有决定的批准权。用户已经明确授权且门槛已满足时继续执行，不新增集体审批。

跨受众发布授权也可与写回同条给出，但须由有权发布的人明确指定具体内容与目标受众；笼统的“整理本线程”不批准公开整个私密讨论。

## 一次请求的闭环

1. **接收。** 核验真实 workspace、频道、线程、发起成员和接收的 agent。保存请求及消息版本，检查重试与已存在的回执；复杂或较慢任务简短确认接收，快速任务只回最终结果。
2. **理解。** 读取原线程、相关已登记 Decision 与目标文档的当前版本。只加载本次需要的来源。Team 执行器通过获准投影核对 Decision，不能读取私密 founders 历史。使用 Wispr 来源时另做其连接、身份与读取前置检查；纯 Slack/docs 请求不依赖 Wispr 连接。
3. **核验。** 确定用户要求的是查询、建议、写回还是发布，并核验来源受众、目标权限与确认依据。独立且已授权的工作继续；所需决定尚未确认时，在原线程提出具体问题，并登记 Decision 待办。私有问题或原文不能因请求来自 Team 就进入 Team。
4. **写入。** 写前重读目标，保留人工内容与既有有效决定，做局部修改。多个文档按目标分别保存待处理/已验证状态。同一文档只交给一个写入者；发现其他成员/agent 同时修改则重读合并或暂停该目标，不覆盖并发内容。
5. **验证与回帖。** 重新加载目标并核对实际结果后，才在原线程报告完成。只回待确认事项、失败缺口或简短结果，不要求成员打开 docs 才能知道发生了什么。

对外状态只需：处理中、待确认、待处理、已完成。待确认表示缺少有权结论；待处理表示访问/执行等缺口。回帖采用“问题／解决方案／目前进度”，完成时写明改了什么、读回结果、仍缺什么及可选文档链接。多目标部分成功就明确列出已完成和未完成；不能以已发起代替已完成。

重大文档更新仍按 [publication.md](publication.md) 向获授权的公司/团队目的地通知。原线程回告与重大更新通知使用各自回执、分别查重；相同事件不因跨入口接收而重复广播。

## 权限、触发与恢复

- 私密 Decision 仅给配置白名单。Founders 与 Team 使用分离的来源、身份、运行上下文和状态；派生内容继承最严格来源受众。私密内容即使已决定，向 Team 发布仍须准确版本与目标的明确批准。
- 原线程是默认回告位置，但回帖前核对当前受众；执行过程中若发现更私密的来源，在原线程只说明缺口，敏感内容移到已授权的私密入口。不能把私有标题、链接、错误原文或内部请求数量带回 Team。
- 召唤走已验证的事件入口，或已配置轮询来发现请求。每次执行均核对有关 Decision；日汇总只汇总实质变化，不承担唯一请求入口。未部署监听时不能把发出 `@` 当作已受理；未开始的请求也不能报告处理中。自动推送和回声不递归触发命令。
- 私有请求记录保存来源事件身份/编辑版本、发起者、受众、目标文档、确认依据、预期变更和逐目标回执。相同事件重投不重复执行；消息被编辑时重新核对变更，旧批准不沿用到新方案。
- 写入结果不明时先查远端目标/消息，确认后续办；docs 成功但回帖失败时只补回帖。保留失败目标与来源 checkpoint，不盲目创建第二份文档、不重置整个队列。本机 ledger 不提供跨运行器的分布式锁或 exactly-once 保证。

## 上线验收

私有运行配置须登记真实 agent ID、允许的频道/受众、执行身份、可访问的 docs 目标、触发方式、工作者和回执存储。至少实测：同受众线程请求可写回并读回；无权成员不能改变有效决定；Team 无法读取 founders 来源；明确且合法的写回无需重复审批；重复事件/部分失败能续办；并发修改被保留；Slack 回帖的结果与 docs 一致。验收通过才启用召唤入口，保存通过的证据，不把 skill/PR 完成当作部署成功。
